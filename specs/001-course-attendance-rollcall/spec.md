# Feature Specification: 課程點名系統（Course Attendance Roll Call）

**Feature Branch**: `001-course-attendance-rollcall`

**Created**: 2026-05-18

**Status**: Draft

**Input**: 我想開發一個課程點名系統，管理員需要可以新增課程名稱和課程時間，可以新增學生的名字和學號。學生的話，可以使用 QR Code 進行點名，管理員可以產生一個 QR Code，QR Code 每 15 秒會更新一次。學生打開 QR Code 的時候，使用 Google 登錄，完成點名。管理員要可以匯出點名的名單，以及學生點名的時間、使用的 IP 和使用的裝置。管理員要可以設定遲到判定﹑紀錄學生請假紀錄﹑自動統計出席率

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理員建立課程與學生名單 (Priority: P1)

管理員登入系統後，可以新增課程（設定課程名稱及上課時間），並將學生（姓名、學號）加入對應課程。這是整個點名系統的基礎資料，其他所有功能都依賴於此。

**Why this priority**: 沒有課程與學生名單，點名流程無法啟動。這是最小可行產品（MVP）的前提。

**Independent Test**: 管理員可以獨立新增一門課程並加入學生名單，驗證資料正確儲存後即可視為功能完整。

**Acceptance Scenarios**:

1. **Given** 管理員已登入系統，**When** 管理員填寫課程名稱與課程時間並送出，**Then** 系統儲存課程並顯示於課程列表中。
2. **Given** 課程已建立，**When** 管理員輸入學生姓名與學號並新增，**Then** 該學生出現於課程學生名單中。
3. **Given** 管理員嘗試新增重複學號的學生，**When** 送出資料，**Then** 系統顯示錯誤提示，拒絕重複新增。
4. **Given** 管理員嘗試新增缺少必填欄位的課程，**When** 送出，**Then** 系統顯示驗證錯誤，要求補填。

---

### User Story 2 - 學生透過 QR Code 完成點名 (Priority: P1)

管理員在課堂中開啟點名模式，系統產生一個動態 QR Code（每 15 秒自動更新）。學生使用手機掃描 QR Code，跳轉至點名頁面並以 Google 帳號登入，系統自動比對 Google 帳號與學號資料，完成點名並記錄時間、IP 位址與裝置資訊。

**Why this priority**: 這是系統的核心功能，點名流程直接決定系統存在的價值。

**Independent Test**: 管理員產生 QR Code，一位學生掃描並以 Google 帳號登入後，管理員可在後台看到該生的點名紀錄（含時間、IP、裝置），即視為功能完整。

**Acceptance Scenarios**:

1. **Given** 管理員已開啟某課程的點名模式，**When** 管理員查看點名頁面，**Then** 畫面顯示 QR Code 並每 15 秒自動刷新，倒數計時器清楚顯示。
2. **Given** 學生掃描當前有效的 QR Code，**When** 學生以已綁定帳號的 Google 帳號登入，**Then** 系統記錄出席，並向學生顯示點名成功的確認訊息。
3. **Given** 學生掃描 QR Code 後進行 Google 登入，**When** OAuth 完成時 Token 已過期但仍在掃描寬限期內（`token_issued_at + grace_period ≥ now`）且 Session 仍為 `active`，**Then** 系統允許完成點名，記錄掃描時的原始時間戳為點名時間。
4. **Given** 學生使用已超過寬限期的過期 QR Code，**When** 嘗試存取，**Then** 系統拒絕並提示 QR Code 已失效，請重新掃描。
5. **Given** 學生使用未綁定 Google 帳號嘗試點名，**When** Google 登入成功後，**Then** 系統顯示找不到對應學生的提示，點名不計入。
6. **Given** 同一學生在同一次課程中已完成點名，**When** 再次掃描並登入，**Then** 系統顯示已點名訊息，不重複記錄。

---

### User Story 3 - 管理員設定遲到判定與請假記錄 (Priority: P2)

管理員可為每門課程設定遲到的判定規則（例如：課程開始後幾分鐘內點名視為準時，超過則標記為遲到）。管理員也可手動為學生新增請假記錄，說明請假原因與日期。

**Why this priority**: 這是出席管理的延伸功能，使統計數據更精確，但不影響基本點名流程。

**Independent Test**: 管理員設定遲到門檻後，模擬不同時間點的點名，驗證系統正確區分準時與遲到；管理員新增請假記錄後驗證該記錄出現在統計中。

**Acceptance Scenarios**:

1. **Given** 管理員進入課程設定，**When** 設定「課程開始後 X 分鐘內為準時」，**Then** 系統儲存設定，並在後續點名時依此規則判定。
2. **Given** 學生在遲到門檻之後點名，**When** 系統記錄出席，**Then** 狀態標記為「遲到」而非「出席」。
3. **Given** 管理員選擇某位學生的某次課程，**When** 新增請假記錄並附上原因，**Then** 系統記錄請假，出席統計中該次課程標記為「請假」。

---

### User Story 4 - 管理員查看自動出席統計與匯出名單 (Priority: P2)

系統自動計算每位學生的出席率（出席次數 / 應出席次數），管理員可一目了然地查看統計結果。管理員可將任一課程的點名記錄（含點名時間、學生 IP 位址、使用裝置）匯出為檔案（預設為 CSV 格式）。

**Why this priority**: 統計與匯出是管理需求，直接影響教師的工作效率，但不影響點名本身的運作。

**Independent Test**: 在有若干點名記錄後，管理員可下載含所有欄位的匯出檔案，並可在統計頁面看到每位學生的出席率百分比。

**Acceptance Scenarios**:

1. **Given** 課程已進行多次點名，**When** 管理員查看出席統計，**Then** 每位學生的出席次數、遲到次數、請假次數及出席率百分比均正確顯示。
2. **Given** 管理員選擇匯出某課程名單，**When** 點擊匯出，**Then** 系統產生包含學生姓名、學號、點名狀態、點名時間、IP 位址、裝置資訊的 CSV 檔案供下載。
3. **Given** 管理員篩選特定日期範圍，**When** 匯出名單，**Then** 匯出的資料僅包含該時間範圍內的記錄。

---

### User Story 5 - 學生查看個人出席記錄 (Priority: P2)

學生以 Google 帳號登入後，可查看自己在所有課程中的個人出席記錄，包含各課次的點名狀態（準時/遲到/請假/缺席）與出席率統計，唯讀不可修改。

**Why this priority**: 學生自我監督出席率，減少主動詢問管理員的行政負擔；資料唯讀，不涉及安全風險。

**Independent Test**: 已完成點名的學生以相同 Google 帳號登入後，可看到個人出席頁面，正確顯示各課程出席狀態與統計，即視為功能完整。

**Acceptance Scenarios**:

1. **Given** 學生已以 Google 帳號完成點名，**When** 學生以同一帳號登入，**Then** 學生可看到個人出席頁面，列出所有已選修課程的出席記錄。
2. **Given** 學生查看個人出席頁面，**When** 頁面載入，**Then** 顯示每門課程的準時次數、遲到次數、請假次數、缺席次數及出席率百分比。
3. **Given** 學生嘗試存取其他學生的出席記錄，**When** 發出請求，**Then** 系統拒絕並顯示權限不足訊息。
4. **Given** 學生尚未與任何課程的 Student 記錄綁定，**When** 以 Google 帳號登入，**Then** 系統顯示「尚未加入任何課程」提示。

---

### Edge Cases

- 學生在同一課次重複掃描多次 QR Code 時，應只記錄第一次有效點名。
- 管理員在點名進行中修改遲到設定時，應明確說明是否溯及當前課次。
- Google 帳號與多位學生的學號綁定衝突時，系統應拒絕並提示管理員處理。
- 學生點名時網路中斷，應提示重新掃描，不應產生錯誤點名記錄。
- QR Code 顯示裝置（管理員端）若斷線，應停止點名並通知管理員。
- 匯出大量點名記錄時，單次匯出上限為 30,000 筆；超過時系統提示管理員縮小日期範圍，不執行超限匯出。目標回應時間 ≤ 30 秒（採同步下載，不使用非同步背景工作）。

## Requirements *(mandatory)*

### Functional Requirements

**課程管理**

- **FR-001**: 系統 MUST 允許管理員新增課程，必填欄位包含課程名稱與定期上課時間；上課時間以結構化欄位儲存：`day_of_week`（0=週日…6=週六）、`start_time`（TIME）、`end_time`（TIME），每門課僅支援一個固定週次時段（如每週二 09:00–12:00）。
- **FR-002**: 系統 MUST 允許管理員編輯既有課程；「刪除課程」採**軟刪除**策略：課程狀態標記為 `archived`，所有關聯資料（AttendanceSession、AttendanceRecord、CourseEnrollment）完整保留，`archived` 課程不可再開新的點名 Session，且不出現在一般課程列表中；管理員 MUST 能在封存列表中查看 `archived` 課程的歷史點名資料。
- **FR-003**: 系統 MUST 允許管理員在課程下新增、編輯、移除學生（姓名、學號）。
- **FR-004**: 系統 MUST 防止同一課程中新增重複學號的學生。

**身份驗證與角色管理**

- **FR-005a**: 系統 MUST 使用 **NextAuth.js** 作為統一認證框架，管理員與學生共用同一 `User` 資料表，以 `role` 欄位區分角色（`admin` / `student`）。
- **FR-005b**: 管理員 MUST 透過 Google OAuth 登入，系統依 `role` 欄位授予管理後台存取權限；初始管理員帳號透過環境變數 `ADMIN_EMAILS`（逗號分隔，如 `a@school.edu,b@school.edu`）設定白名單，應用啟動時讀取；白名單中的 Email 首次以 Google OAuth 登入時，系統自動將其 `role` 設為 `admin`。
- **FR-005d**: 已登入的管理員 MUST 能在後台管理介面中將任意已登入過的 Google 帳號提升為管理員（`role: admin`）或降回學生（`role: student`）；此操作 MUST 記錄稽核日誌（操作者、目標帳號、時間）。
- **FR-005c**: 學生首次以 Google 帳號掃描 QR Code 登入時，系統自動建立 `User` 記錄並將 `role` 設為 `student`。

**Google 帳號綁定**

- **FR-005**: 系統 MUST 允許將學生的 Google 帳號（email）與學號進行綁定，以便點名時自動識別。`Student.google_email` 欄位 MUST 設置資料庫層唯一約束（Unique Index），確保同一 Google Email 不可對應兩筆 Student 記錄；CSV 批次匯入或手動新增時若 Email 重複，系統 MUST 拒絕寫入並回報錯誤。
- **FR-006a**: 管理員 MUST 能透過上傳 CSV 檔案批次匯入學生資料，CSV 必填欄位為：學號、姓名、Google Email；系統採**部分匯入**策略：有效列逐筆寫入，無效列略過；匯入完成後 MUST 回報成功筆數、略過列數，以及每列的錯誤行號與原因（如格式不符、欄位缺漏）。
- **FR-006b**: 管理員 MUST 能在後台手動逐筆新增單一學生（學號、姓名、Google Email）作為補救機制（如補修課、遲加選學生）。

**QR Code 點名**

- **FR-007**: 系統 MUST 允許管理員為特定課程開啟一次點名 Session；Session 具有四種狀態：`active`（進行中）、`closed`（手動關閉）、`expired`（自動逾時）、`voided`（作廢）。管理員 MUST 能將任意非 `active` 狀態的 Session 標記為 `voided`；`voided` Session 不計入出席率分母，其下所有點名記錄仍保留但不計入統計；此操作 MUST 記錄稽核日誌（操作者、Session ID、操作時間、作廢原因）。
- **FR-007a**: 管理員 MUST 能隨時手動關閉進行中的點名 Session。
- **FR-007b**: 管理員 MUST 能在開啟 Session 時設定自動逾時時間（單位：分鐘）；時間到後系統自動將 Session 標記為 `expired`，QR Code 立即失效。
- **FR-007d**: 管理員 MUST 能在開啟 Session 時設定 **QR Code 掃描寬限期**（單位：秒，預設 60 秒）；寬限期定義為：學生掃描 QR Code 取得 Token 後，允許 Token 在 OAuth 流程完成前過期的容忍時間。系統驗證點名請求時，若 `token_issued_at + grace_period_seconds ≥ now` 且 Session 仍為 `active`，則視為有效點名。
- **FR-007c**: 同一課程在同一時間 MUST 只能有一個 `active` 的點名 Session。
- **FR-008**: 系統 MUST 產生動態 QR Code，QR Code 每 15 秒自動更新為新的有效碼，舊碼立即失效。Token 採 **HMAC 簽名**機制（以 Session ID + 時間戳 + 伺服器密鑰產生），伺服器驗簽時不需額外儲存當前 Token，可直接驗證真實性與有效期；任何竄改或過期的 Token 均被拒絕。
- **FR-009**: 系統 MUST 在 QR Code 旁顯示倒數計時，告知管理員和學生距離下次更新的秒數。
- **FR-010**: 學生掃描 QR Code 後，MUST 跳轉至點名頁面並透過 Google OAuth 登入。
- **FR-011**: 系統 MUST 在 Google 登入成功後，自動比對 Google 帳號與已綁定的學號，完成點名記錄。
- **FR-012**: 系統 MUST 記錄每次點名的時間戳記、學生 IP 位址、使用裝置的 User-Agent 資訊。
- **FR-013**: 系統 MUST 拒絕同一學生在同一課次重複點名，並向學生顯示已完成點名的提示。
- **FR-014**: 系統 MUST 拒絕使用過期 QR Code 的點名請求，並提示重新掃描；例外：若 Token 在掃描寬限期（FR-007d）內，且 Session 仍為 `active`，則允許完成點名。

**遲到管理**

- **FR-015**: 管理員 MUST 能為每門課程設定遲到判定門檻（課程開始後 N 分鐘內點名視為準時）。管理員在開啟 AttendanceSession 時，MUST 能自訂該次課程的「官方開始時間」，預設帶入 Course 排定的上課時間，允許臨時調整（如補課、換教室延誤）；此官方開始時間為該次遲到判定的唯一基準。
- **FR-016**: 系統 MUST 依遲到設定自動將點名狀態標記為「出席（準時）」或「遲到」。

**請假管理**

- **FR-017**: 管理員 MUST 能為學生新增特定課次的請假記錄，需填寫原因。
- **FR-017a**: 管理員 MUST 能在任意時間手動新增或覆寫學生的出席記錄（指定課次、學生、狀態），涵蓋系統故障補登與人工修正兩種情境（例如將系統自動判定的「遲到」改為「準時」）；操作 MUST 記錄稽核日誌，包含：操作者、操作時間、原始狀態值、新狀態值、修改原因。
- **FR-018**: 系統 MUST 將請假記錄反映在出席統計中，與缺席分開統計。

**出席統計**

- **FR-019**: 系統 MUST 自動計算每位學生的出席率（出席次數 / 應出席課次），並分別顯示準時、遲到、請假、缺席的次數。「應出席課次」定義為管理員實際開啟過且狀態**非** `voided` 的 AttendanceSession 總數；未開啟 Session 的排定週次及 `voided` Session 均不計入分母。
- **FR-020**: 管理員 MUST 能查看課程的整體出席統計總覽。

**匯出功能**

- **FR-021**: 管理員 MUST 能匯出任一課程的完整點名記錄，格式為 CSV（唯一支援格式，不提供 .xlsx），包含欄位：學生姓名、學號、課次日期、點名狀態、點名時間、IP 位址、裝置資訊。
- **FR-021a**: 系統 MUST 在執行含 PII（IP 位址、裝置資訊）的匯出操作前，顯示個人資料使用警告提示，需管理員確認後才執行下載。
- **FR-021b**: 系統 MUST 記錄每次匯出操作的稽核日誌，包含：執行者（管理員 Email）、操作時間、匯出範圍（課程、日期區間）。
- **FR-021c**: 管理員 MUST 能在後台手動刪除特定學生的所有個人資料（User 記錄、點名記錄中的識別欄位），以支援個資法的部分合規需求；刪除操作 MUST 記錄稽核日誌，且需二次確認。
- **FR-022**: 管理員 MUST 能依日期範圍篩選後再匯出；單次匯出筆數上限為 30,000 筆，超過時系統 MUST 顯示提示並拒絕執行，要求管理員縮小範圍後重試。

**稽核日誌**

- **FR-024**: 系統 MUST 將所有稽核事件（匯出操作、手動補登、作廢 Session、角色變更、個資刪除）同時寫入結構化 JSON 日誌檔案（符合 TC-006）並持久化至資料庫專屬稽核表（`AuditLog`）。管理後台 MUST 提供專屬「稽核日誌」頁面，管理員可依事件類型、操作者、日期範圍篩選並查看所有稽核記錄；稽核記錄僅限管理員查看，不可刪除或修改。

**學生自助查詢**

- **FR-023**: 系統 MUST 提供學生個人出席記錄查詢頁面，學生以 Google 帳號登入後，可唯讀查看自己在所有課程中的點名狀態與出席率統計；系統 MUST 確保學生只能存取自身資料，不可存取其他學生記錄。學生與管理員共用同一 `/login` 頁面（Google OAuth），登入後依 `role` 欄位自動導向：`role=student` → 個人出席頁；`role=admin` → 管理後台。

### Key Entities

- **課程（Course）**: 代表一門課，包含課程名稱、定期上課時間（`day_of_week` + `start_time` + `end_time`，單一週次時段）、遲到判定設定、狀態（`active` / `archived`）；對應多位學生與多次點名記錄。`archived` 課程資料完整保留但不可再開點名。
- **使用者（User）**: NextAuth.js 管理的認證記錄，包含 email、name、role（`admin` / `student`）；由 Google OAuth 首次登入時自動建立。
- **學生（Student）**: 學籍檔案，包含姓名、學號、綁定的 Google Email（可為 null，首次掃描 QR Code 後自動關聯至 User FK）；由管理員預先建立（CSV 批次或手動逐筆）。
- **選課記錄（CourseEnrollment）**: 多對多關聯表，記錄哪位 Student 選修哪門 Course；同一學生可同時修多門課（student_id + course_id 為複合唯一鍵）。
- **點名Session（Attendance Session）**: 代表單次課堂的點名活動，包含 Session 建立時間、**官方課程開始時間**（管理員開啟時設定，預設帶入排定時間，為遲到判定基準）、所屬課程、狀態（`active` / `closed` / `expired` / `voided`）、自動逾時設定（分鐘數）、**QR Code 掃描寬限期**（秒數，預設 60，管理員開啟 Session 時可調整）。`voided` 狀態代表管理員誤開後主動作廢，不計入出席率分母。QR Code Token 以 HMAC 簽名動態產生（Session ID + 時間戳 + 密鑰），不需在資料庫中持久化當前 Token 值。
- **點名記錄（Attendance Record）**: 代表學生在某次Session的出席紀錄，包含狀態（準時/遲到/請假/缺席）、點名時間、IP 位址、裝置資訊。
- **請假記錄（Leave Record）**: 代表學生的請假申請，包含所屬課次、原因、建立者（管理員）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理員可在 2 分鐘內完成新增一門課程（含課程時間設定）並加入 30 位以上學生。
- **SC-002**: 學生從掃描 QR Code 到點名完成（包含 Google 登入），全程在 30 秒內完成。
- **SC-003**: QR Code 更新延遲不超過 1 秒（即實際顯示的新碼在計時器歸零後 1 秒內切換）。
- **SC-004**: 系統能同時支援同一課程 100 位學生在 15 秒內完成點名，不出現錯誤或漏記。
- **SC-005**: 出席統計資料在最後一筆點名完成後立即（5 秒內）反映於統計頁面，無需手動刷新。
- **SC-006**: 100 位學生、20 次課程的完整點名記錄可在 10 秒內完成 CSV 匯出；最大規模（30,000 筆上限）的同步匯出目標回應時間 ≤ 30 秒。
- **SC-007**: 過期 QR Code 的點名請求 100% 被系統拒絕，不產生任何有效記錄。
- **SC-008**: 管理員可在 1 分鐘內找到並查看任意學生的個別出席統計與請假記錄。
- **SC-009**: 系統正式環境可用性目標為 99.5%（每月容忍停機 ≤ 3.6 小時）；系統故障期間管理員可透過手動補登功能維持出席記錄完整性。

## Technical Constraints

- **TC-001**: 後端使用 **Next.js（最新版本）** 全端框架（App Router），同時負責前端 UI 與 API Routes。
- **TC-007**: 系統時區固定為 **UTC+8（台灣時區）**，不支援多時區；所有時間戳記（點名時間、Session 建立時間、遲到判定基準等）均以 UTC+8 儲存與顯示；CSV 匯出欄位亦以 UTC+8 輸出，不做時區轉換。
- **TC-002**: 資料庫使用 **PostgreSQL（最新版本）**，透過 Prisma ORM 進行資料存取。
- **TC-003**: 整個應用以 **Docker** 容器化部署，提供 `docker-compose.yml` 以便本地開發；正式環境部署至 **Zeabur 或雲端 VPS**（如 GCP、AWS、Hetzner），PostgreSQL 使用平台托管服務或獨立 VPS 上的容器實例。Google OAuth Callback URL 需於部署後設定為正式域名。
- **TC-004**: 前端採用 Next.js 內建的 SSR／SSG 能力，管理員介面以桌面瀏覽器為主，學生點名頁以手機瀏覽器為主。
- **TC-005**: QR Code 每 15 秒輪換（管理員畫面）與出席統計即時刷新（SC-005）均採用 **SSE（Server-Sent Events）** 實現，透過 Next.js App Router 的 Route Handler 提供 `text/event-stream` 端點，前端以 `EventSource` API 訂閱；不使用 WebSocket 或 client polling。
- **TC-006**: 應用程式 MUST 輸出**結構化 JSON 日誌至檔案**（不依賴外部錯誤追蹤服務）；Docker 部署時需掛載 Volume 以確保容器重啟後日誌持久化，並設定 log rotation 避免磁碟耗盡；日誌內容至少包含：時間戳、日誌層級、請求路徑、錯誤訊息與 Stack Trace（錯誤發生時）。

## Assumptions

- 系統目標使用者為大學或專科院校的課程管理需求，單一課程學生人數預計不超過 200 人。
- 管理員（教師）已具備基本的網頁操作能力，無需特別培訓即可使用系統。
- 學生均有 Google 帳號，且可接受使用 Google 帳號登入進行點名。
- 學生的 Google 帳號與學號的初始綁定由管理員在後台完成（批次匯入或逐一設定），不需要額外的學生自助綁定流程（v1 版本）。
- 管理員的螢幕（或投影設備）用於顯示 QR Code，學生使用個人手機掃描。
- 系統支援桌面瀏覽器（管理員端）和手機瀏覽器（學生端），不需要原生 App。
- 請假記錄的核實（如附件證明）不在本系統範疇內，僅做文字記錄。
- 每週定期課程的點名Session需要管理員手動開啟，系統不自動開啟點名。
- 資料保留策略依學校規定，預設保留至少兩學年的點名記錄。
- 個資法合規責任由學校作為資料控制者承擔；系統層面僅需確保：（1）存取控制（僅管理員可存取完整點名記錄）、（2）匯出稽核日誌、（3）管理員可手動刪除學生個人資料，不需提供學生自助申請刪除的入口。

## Clarifications

### Session 2026-05-18

- Q: 系統的技術堆疊與部署平台為何？ → A: Docker + PostgreSQL + Next.js（最新版本）
- Q: 管理員如何登入系統，採用哪種身份驗證架構？ → A: NextAuth.js 多角色（Role-based），管理員與學生共用 User 資料表，以 role 欄位區分
- Q: 學生 Google 帳號與學號的綁定方式為何？ → A: CSV 批次匯入（主）＋ 手動逐筆新增（補）
- Q: 點名 Session 如何結束，是否有自動逾時機制？ → A: 手動關閉為主，可設定自動逾時分鐘數
- Q: 含 PII（IP、裝置）的點名記錄有無隱私保護機制？ → A: 匯出前顯示個資警告 ＋ 記錄匯出稽核日誌
- Q: QR Code 每 15 秒輪換與統計即時更新的技術實現機制為何？ → A: SSE（Server-Sent Events）— 伺服器主動推送，Next.js App Router 原生支援
- Q: 出席率分母「應出席課次」的計算依據為何？ → A: 以管理員實際開啟過的 AttendanceSession 數量為準，未開啟 Session 的週次不計入分母
- Q: 初始 Email 白名單設定後，如何新增或移除其他管理員帳號？ → A: 已登入的管理員可在後台 UI 中將其他 Google 帳號提升或降為管理員
- Q: 系統是否需要實作台灣個資法主動合規機制（如學生申請刪除資料）？ → A: 部分合規 — 確保存取限制與保留期限設定；管理員可手動刪除學生個人資料，無需學生自助刪除入口
- Q: 匯出功能是否需要支援 Excel（.xlsx）格式？ → A: 否，僅支援 CSV；不引入額外的 xlsx 依賴
- Q: User 資料表與 Student 實體的資料庫 Schema 關係為何？ → A: 三張表 — User（NextAuth 認證）+ Student（學生檔案，含可為 null 的 User FK）+ CourseEnrollment（多對多 student_id ↔ course_id）；學生記錄由管理員預建，首次掃描 QR Code 後補上 User FK
- Q: 遲到判定「課程開始時間」的基準為何？ → A: 管理員開啟 Session 時可自訂「官方開始時間」，預設帶入 Course 排定時間，允許臨時調整；此時間為該次遲到判定的唯一基準
- Q: 同一學生是否可同時選修多門課程？ → A: 是，CourseEnrollment 為多對多關聯表（student_id + course_id 複合唯一鍵），同一學生可選修多門課
- Q: 正式上線的部署環境為何？ → A: Zeabur 或雲端 VPS（如 GCP、AWS、Hetzner）；PostgreSQL 使用平台托管或 VPS 容器；本地開發維持 docker-compose
- Q: 系統可用性目標為何？ → A: 99.5%（每月容忍 ~3.6 小時停機）；需提供管理員手動補登出席的備援機制，避免系統故障導致記錄遺失
- Q: 學生在完成 QR Code 點名後，是否能夠自行查看個人的出席記錄？ → A: 是，學生可以 Google 帳號登入後，查看自己在所有課程的出席記錄（唯讀）
- Q: QR Code 動態 Token 的安全性機制為何？ → A: HMAC 簽名 Token（Session ID + 時間戳 + 伺服器密鑰），伺服器直接驗簽，無需持久化當前 Token
- Q: 系統是否需要整合應用層級的錯誤監控服務？ → A: 否，輸出結構化 JSON 日誌至檔案（需 Volume 掛載持久化 + log rotation），不引入外部錯誤追蹤服務
- Q: 管理員補登功能是否能覆寫系統已自動產生的出席記錄？ → A: 是，可覆寫任何狀態；稽核日誌需記錄原始值、新值、操作者與修改原因
- Q: 大量匯出的策略與上限為何？ → A: 同步下載，單次上限 30,000 筆，超過時提示縮小範圍；目標回應時間 ≤ 30 秒，不使用非同步背景工作
- Q: 學生掃描 QR Code 後進行 Google OAuth 期間 Token 過期，點名是否仍有效？ → A: 加入可設定寬限期（預設 60 秒），管理員開啟 Session 時可調整；寬限期內且 Session 仍 active 則視為有效
- Q: CSV 批次匯入發生驗證錯誤時，行為為何？ → A: 部分匯入 — 有效列成功匯入，無效列略過並回報錯誤行號與原因，不因部分錯誤拒絕整份檔案
- Q: Google Email 唯一性應在哪個層級強制執行？ → A: 資料庫層唯一約束（Student.google_email Unique Index），寫入時即攔截重複 Email，不等到登入時才偵測
- Q: 系統時區處理方式為何？ → A: 固定 UTC+8（台灣時區），不支援多時區；所有時間戳記儲存、顯示與 CSV 匯出均以 UTC+8 輸出
- Q: 管理員誤開 Session 時有無補救機制？對出席率分母是否有影響？ → A: 新增 `voided` 狀態，管理員可作廢誤開的 Session；`voided` Session 不計入出席率分母，操作記錄稽核日誌
